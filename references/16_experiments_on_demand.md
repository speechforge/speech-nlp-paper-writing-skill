# Experiments on Demand (Close Evidence Gaps Without Drowning in Logistics)

A paper is a claim-evidence structure. When a claim lacks evidence, the right responses are, in order: **run the missing experiment, bound the claim, or remove it.** This file is the cheap, disciplined way to do the first. The goal: the model spends its tokens thinking and writing, not babysitting jobs.

---

## 1. When to trigger the loop

Run it when any of these is true:

- A claim row is `Needs experiment` or `Needs evidence` and a controlled run would settle it.
- The results table has no seeds, no uncertainty, a missing baseline, or an unmatched compute budget (`context_digest.md` flags these).
- A skeptical review (`20`) names a missing ablation, a confound, or an out-of-distribution test that is the main rejection risk.
- A number in the draft cannot be traced to a results file.

Do **not** run experiments to search for a result that flatters the paper. Write the hypothesis and success criterion first, and report the outcome whichever way it falls. A negative or mixed result is a scope constraint and belongs in the paper.

---

## 2. The loop

```
gaps  ->  brief  ->  (user approves cost)  ->  run (background, quiet)  ->  status  ->  ingest  ->  update the claim map and the text
```

| Step | Command | What the agent reads |
|---|---|---|
| Find gaps | `experiments.py gaps PROJECT` | one line per open claim |
| Write the prompt | `experiments.py brief PROJECT --title T --claims 1,3 --hypothesis H --gpu-hours 2` | creates `experiments/briefs/EXP-00N.md` |
| Complete the protocol | edit the brief's `[INSERT]` lines: data and splits, baselines, metrics and toolkit versions, seeds, listener protocol | the brief |
| Get approval | show the user the hypothesis, protocol, and budget; then `experiments.py approve PROJECT EXP-001` | the user's answer |
| Run | `experiments.py run PROJECT EXP-001 -- <command>` | one confirmation line |
| Wait | `experiments.py status PROJECT` | one status line per experiment |
| Collect | `experiments.py ingest PROJECT EXP-001 results.csv --summary "..."` | `experiments/results/EXP-001.summary.md` (about six lines) |
| Failure only | `experiments.py tail PROJECT EXP-001 -n 20` | the last 20 log lines |

### The brief is the experiment prompt
The brief is **self-contained**: goal, why (which claim), exact protocol, deliverable schema, rules, and a done condition. Hand it to whatever runs the work: the user's lab, another coding agent, or a shell command. It tells the runner to log to a file, print at most eight summary lines, keep the evaluation code fixed across systems, use at least three seeds, and stop at the budget.

### Approval and budget
Running costs time and money, so the default is **ask once per experiment, with the budget stated**. The user can pre-authorise in `project_meta.json` (`experiments.auto_run: true`, `max_gpu_hours_per_experiment`). `run` refuses an unapproved experiment and a brief that still contains `[INSERT]`.

### Token discipline
- Never read raw logs unless `status` says `failed`; then read the last 20 lines only.
- Read the ingested **summary**, not the CSV, to write results prose; open the CSV only to copy exact figures.
- Experiments run **detached**; the agent does not poll in a loop. Check `status` when the user returns or when the next step needs the result.
- One brief per group of related claims, not one per sentence.

---

## 3. What counts as valid evidence

- Declared data, splits, and leakage controls; speaker-independent splits for speech.
- Matched compute and tuning budget across systems; baselines run with their recommended settings.
- At least three seeds with mean and sample standard deviation, or a paired test, or a bootstrap interval; for human evaluation, listener or annotator counts and agreement.
- The same evaluation code for every system; metric toolkit and version recorded.
- Out-of-distribution claims need genuinely unseen speakers, domains, or languages, and robustness claims need declared perturbation curves.

Anything weaker becomes bounded wording ("on the evaluated corpus", "in this single run") or a stated limitation.

---

## 4. Writing the outcome back

1. `ingest` copies the results to `experiments/results/`, writes the summary, links the claim rows to the experiment, and downgrades `Needs experiment` to `Needs evidence`.
2. Read the summary, copy exact numbers into the section file and into a figure or table via the deterministic tools (`14`).
3. Set each linked claim to `Supported`, `Partial`, or reword or remove it. Update `Scope limit`.
4. Re-run `paper_check.py PROJECT ready`; the dashboard shows the experiment as ingested.

Numbers in the paper must trace to the ingested results file, never to a log line, a chat message, or memory.

---

## 5. Prompt for the experiment runner (template used in the brief)

The brief generated by `experiments.py brief` already contains this. In outline:

> **Goal:** [hypothesis and success criterion]. **Protocol:** [data and splits, systems and budgets, metrics with direction and toolkit version, seeds >= 3, human-evaluation protocol if any]. **Deliverable:** one CSV, one row per (system, condition, seed), with a column per metric. **Rules:** do not change evaluation code between systems; log to a file; print at most eight lines at the end; stop at the budget; if a run fails, report the last 20 log lines and stop. **Never** put file names, commands, or identifiers into paper text.

---

## 6. Scope guard

Experiments exist to **support or bound claims already in `claim_evidence_map.md`**. Do not start new research directions inside a writing task; record them under "future work" or as a new brief only if the user asks.
